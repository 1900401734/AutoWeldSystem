# 设备状态 JSONL 单一数据源设计

## 背景

设备状态目前同时写入 `Biz_DeviceStatusLog` 和 `DeviceStatus/*.jsonl`。日志管理在 JSONL 为空时回退数据库，导致现场删除 JSONL 后，界面仍重新显示已删除记录。设备状态上传任务也复制了数据库日志内容，列表过滤和实际执行使用的来源不完全一致，可能出现页面已隐藏但任务仍可上传的情况。

本设计将设备状态 JSONL 设为唯一事实来源。`Biz_UploadTask` 继续承载通用上传执行信息，但只能作为 JSONL 的派生索引，不能独立证明某条设备状态仍应显示或上传。

## 目标

- 设备状态只通过 `DeviceStatus/*.jsonl` 创建、查询、更新和删除。
- 状态码固定为 `0=停机`、`1=开机`、`4=异常`、`5=异常恢复`、`6=程序执行开始`、`7=程序执行结束`。
- 只有状态发生变化或调用方明确要求强制记录时才新增状态事件。
- 每条状态必须先成功落盘，随后才能通知日志 UI、上传 MES 或生成补传任务。
- JSONL 中最新版本为 `Pending` 或 `Failed` 的记录出现在待上传数据的设备状态页签。
- JSONL 记录被外部删除后，刷新或重新进入页面时不再显示，也不再参与单条或批量上传。
- 停止创建和读写 `Biz_DeviceStatusLog`，避免数据库与文件双来源继续分叉。

## 非目标

- 不删除现场已有的 `Biz_DeviceStatusLog` 物理表。
- 不把旧表数据迁移或补写到 JSONL。
- 不撤销已经成功完成的 MES 上报。
- 不为外部文件删除增加 `FileSystemWatcher` 或轮询任务。
- 不取消通用 `Biz_UploadTask` 表，也不重写其他上传类型的执行框架。

## 唯一来源不变量

1. JSONL 中不存在设备状态记录时，日志 UI、补传 UI 和上传执行器都视为不存在该状态。
2. `Biz_UploadTask` 中存在设备状态任务，不能覆盖来源缺失这一事实。
3. 新状态在第一次 JSONL 追加成功前，不得调用 MES、创建补传任务或通知 UI。
4. 每次设备状态任务执行前必须重新读取 JSONL，不能只依赖任务行或其旧 payload。
5. 同一状态事件的最后一个追加版本表示最新上报状态。
6. 已上传任务不因来源文件被删除而回退、重试或撤销；缺失来源只清理未成功任务。

## 数据模型与兼容标识

设备状态改用普通 JSONL 日志模型，不再作为 SqlSugar 实体。新日志增加 `RecordId`，创建时使用 `Guid.NewGuid().ToString("N")` 生成。

记录关联键按以下顺序解析：

1. `RecordId` 非空时直接使用规范化后的 GUID 字符串。
2. 旧 JSONL 没有 `RecordId` 且原整数 `Id` 大于零时，使用 `legacy:{Id}`。
3. 两者都不存在时，该记录缺少可靠身份：读取时跳过并写程序异常日志，不允许进入补传。

旧 JSONL 的字段名称和多行 JSONL 格式保持兼容。新记录不再依赖数据库自增 `Id`；旧 `Id` 仅用于历史文件兼容。上传任务使用记录关联键作为 `BusinessId` 和 payload 中的定位信息，不再复制设备状态正文作为权威数据。

同一个 `RecordId` 可以追加多个版本，例如 `Pending -> Failed -> Uploaded`。读取时按文件追加顺序保留最后版本，并按 `OccurredTime` 倒序展示。

## 组件职责

### DeviceStatusLocalLogStore

- 负责生成日志目录和按日期定位 JSONL。
- 串行化同一进程内的追加、读取和重写，避免双工位并发写入破坏记录边界。
- 提供按日期读取、读取全部最新版本、按工位读取最新状态、按关联键查找和判断来源是否存在的能力。
- 按记录关联键去重和删除，兼容新 `RecordId` 与旧整数 `Id`。
- 读取失败、无目录或无文件时返回空结果，不访问数据库。

### DeviceStatusService

- 不再查询、插入、更新或删除 `Biz_DeviceStatusLog`。
- 从 JSONL 获取当前状态、各工位最新状态和重复判断基准。
- 创建新状态时先构造 `Pending` 记录并落盘；禁用设备状态上报时直接构造并落盘 `Skipped` 版本。
- 首次落盘失败时写程序异常日志并终止该记录流程，不通知 UI、不上传、不生成任务。
- 首次落盘成功后发布 `LogsChanged`，由日志管理和待上传页面重新读取来源。
- MES 在线时立即上传；MES 离线或上传失败时创建或同步派生上传任务。
- 将 MES 结果以相同 `RecordId` 追加为 `Uploaded` 或 `Failed` 版本，再通知两个 UI 刷新。
- 删除操作只重写 JSONL 并软删除相关未成功上传任务，不再操作设备状态表。

### UploadTaskService

- 设备状态任务只保存记录关联键和通用执行元数据。
- 列表加载前读取 JSONL 最新版本，创建或同步 `Pending/Failed` 的派生任务。
- JSONL 中缺失、已 `Uploaded` 或已 `Skipped` 的来源不出现在待上传设备状态页签。
- 来源缺失时软删除关联的未成功任务；已经 `Uploaded` 的任务保持不变。
- `ExecuteAsync`、`ExecuteAllPendingAsync`、单条重试和全部重试都在改变任务状态或调用 MES 前校验来源。
- 实际 MES 请求从 JSONL 最新版本构造；旧任务只有整数 `LogId` 时转换为 `legacy:{LogId}` 查找旧 JSONL。
- 上传结果必须先成功追加到 JSONL，随后任务行才能按该结果完成同步。

### UI、设备 API 与中心遥测

- `LogManageView` 只显示 JSONL。点击现有刷新入口或重新进入页面时重新读取当前日期；不监听外部文件系统。
- `StateManageView` 只显示由 JSONL 最新版本派生的未成功设备状态任务。
- 两个页面复用 `LogsChanged` 刷新，不再同时维护会产生重复行的实时追加事件。
- `GET /api/DeviceStatus` 从 JSONL 获取最新 MES 状态；没有任何有效记录时返回失败“暂无设备状态记录”，不伪造默认开机状态。
- `CenterTelemetrySyncService` 通过 `IDeviceStatusService` 获取工位最新状态，不再直接查询设备状态表。实时 PLC 状态优先；PLC 也无有效状态时上报空值并显示未知。

## 状态写入与上传流程

### 新状态事件

1. 规范化并校验 MES 状态码和工位。
2. 从 JSONL 读取该工位最新状态，执行现有普通状态、程序边界和强制生命周期去重规则。
3. 创建带 GUID `RecordId` 的日志对象。
4. 上报功能关闭时，将其标记为 `Skipped` 后落盘并刷新 UI，流程结束。
5. 上报功能开启时，先以 `Pending` 追加 JSONL。
6. 首次追加失败时记录程序异常并结束，不调用 MES。
7. 首次追加成功后刷新 UI。
8. MES 离线时同步派生任务，保持 JSONL 为 `Pending`。
9. MES 在线时调用接口，并将结果以相同 `RecordId` 追加为 `Uploaded` 或 `Failed`。
10. `Failed` 结果同步派生任务；`Uploaded` 结果不进入待上传页。

### 补传执行

1. 从任务中解析记录关联键。
2. 从 JSONL 读取该键的最新版本。
3. 来源缺失或状态不再是 `Pending/Failed` 时，不调用 MES，并同步软删除或完成任务投影。
4. 来源有效时使用 JSONL 字段构造 `ReportDeviceStatusReq`。
5. 调用 MES 后，将结果追加到 JSONL。
6. JSONL 结果追加成功后，再更新任务行和刷新 UI。

### 外部删除

外部删除单个日期文件或整个 `DeviceStatus` 目录后，当前已绑定列表不会通过文件监听器立即变化。用户点击刷新、切换后重新进入页面或发起重试时，系统重新读取 JSONL：

- 日志管理不再显示已删除记录。
- 待上传设备状态页不再显示对应未成功记录。
- 相关未成功任务被软删除，单条和批量执行均不能调用 MES。
- 已上传任务和已经发生的 MES 结果不做修改。

## 异常处理

- 首次 JSONL 写入失败：记录程序异常，停止该状态的 UI、MES 和补传流程。
- MES 请求失败：追加 `Failed` 版本并创建派生任务。
- MES 请求完成但结果版本追加失败：记录程序异常，保留 JSONL 中原有的未成功版本，并让任务保持可重试。若 MES 实际已经成功，后续可能再次调用 MES，这是坚持单一来源时的明确边界。
- JSONL 损坏或记录身份无效：跳过无效记录并记录程序异常，其他有效记录继续加载。
- 外部删除与应用读取发生竞争：本次读取按空结果处理，下一次刷新重新计算，不回退数据库。

## 数据库兼容

- 从 `SqlSugarDbContext` 的 CodeFirst 类型列表中移除设备状态表模型，新的数据库不再创建该表。
- 现场已有物理表不执行 `DROP TABLE`，保留原数据以降低升级风险，但运行时代码永久忽略。
- `Biz_UploadTask` 继续使用现有软删除、重试次数和通用状态字段。
- 旧设备状态任务只有整数 `LogId` 时仍可通过旧 JSONL 关联；JSONL 中不存在对应记录时按来源缺失处理。

## README

本次变更影响用户可见日志、补传行为、数据来源和现场排障方式，必须同步更新 `README.md`，说明：

- 设备状态 JSONL 目录是唯一事实来源。
- 删除文件会同时移除日志可见性和未成功状态的补传资格。
- 已完成 MES 上传不会因本地文件删除而撤销。
- 落盘失败时设备状态不会上传，并应到程序异常日志排查磁盘、目录和权限问题。

## 验证

按 TDD 先添加并观察以下回归用例失败，再实现最小代码：

- 新 GUID 标识、旧整数标识、追加版本去重和按键删除。
- JSONL 为空或被删除时不回退 `Biz_DeviceStatusLog`。
- 新状态首次落盘失败时不调用 MES、不创建任务、不通知设备状态 UI，并写程序异常日志。
- 六个合法状态码和主要状态变化来源保持正确。
- `Pending/Failed` 派生任务，`Uploaded/Skipped` 不派生任务。
- 来源缺失时列表同步、单条执行和批量执行均软删除未成功任务且不调用 MES。
- 来源删除不改变已上传任务。
- 设备状态 API 在无 JSONL 时返回失败。
- 中心遥测通过设备状态服务读取 JSONL 回退状态。
- 日志管理刷新和重新进入时重新读取 JSONL。
- 源码中不再存在 `Biz_DeviceStatusLog` 的运行时查询、写入或 CodeFirst 注册。
